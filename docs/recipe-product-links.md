# Recipe details and product links

Recipe details use one scrollable content area between the modal header and action footer. Cost summary amounts come directly from the existing `costBreakdown` calculation, with full internal precision. Missing ingredient costs or conversions remain visible outside the collapsed disclosure. Original method text and structured step order are preserved.

The canonical relationship remains `products.recipeId` (and its existing workspace-scoped database foreign key). One product has one source recipe; several products may share a recipe. `products.unitsPerPackage` retains its existing meaning: the quantity of recipe output used per sellable package. Link review records an explicitly confirmed quantity in the recipe output unit, a selling-unit label, and review metadata in the existing product JSON. It does not create another costing system or relationship table.

`POST /api/workspace`, action `productRecipeLink`, accepts a product ID, recipe ID, current expected recipe ID and confirmed mapping. The server resolves both records inside the verified workspace transaction, restricts changes to Owner/Manager, checks replacement confirmation, and makes identical retries a no-op. It preserves all other product fields. Where both recipe batch packaging and product packaging exist, users must confirm they are distinct costs or correct the existing setup first. Labor and overhead remain part of the existing recipe calculation.

Unlink requires confirmation and removes only the source recipe association and its review metadata. It preserves the stored output quantity, product identity, SKU, photos, price, inventory and history. Current recipe-based product estimates become unavailable until another recipe is linked. Historical production and sales snapshots are unchanged.

Create new product remains the existing secondary creation form; cancelling performs no save, and saving uses the existing product validation and recipe foreign key. A forward migration made the existing `products.recipe_id` column nullable so unlinking can persist without deleting the product. It retained the composite workspace foreign key, existing relationship cardinality, data, and security policies. The generated migration was placed after the applied migration versions; no applied migration was changed.

Automated tests exercise the real workspace handler using a transactional database mock, plus component tests and browser tests with workspace API fixtures. They cover link/relink conflicts, mapping requirements, duplicate retries, unlink safety, cost reuse, protected fields and absence of inventory/accounting writes. Browser fixtures can verify refresh behavior but do not establish persistence in the deployed database or across a real sign-in.
