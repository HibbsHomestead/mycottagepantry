# Optional package-photo import proposal

Approved by the user on November 7, 2026 for a separate implementation. The photo reader, transient image handling and draft review were implemented separately from catalog lookup; see [implementation and actual verification](catalog-and-photo-implementation.md). Nutrition remains outside this feature.

## Compact workflow

Preserve the existing Product URL and Barcode controls at the top of Add/Edit Ingredient Details, followed by manual fields. Add a collapsed Read package photos row with optional Front photo and Back / label photo inputs plus up to two optional close-ups. Either side alone is valid. Each chosen image has a small preview, Rotate, Replace and Remove control. Images selected for reading are separate from the ingredient's chosen product photo.

One Extract from photos action sends all selected images in one request and returns one combined review. Reuse the compact checkbox pattern and the same ingredient draft: usable empty fields preselected; conflicting nonempty values shown beside the imported value and unchecked; uncertain values unchecked; Select all/Clear and one Apply selected values action. Show full text through inline expansion, with no nested scrolling textboxes. Results, errors, and retries stay in the popup. Apply changes only the draft; Cancel/Remove and failed retries leave manual values and existing images untouched.

The URL importer currently has an intentional blank-field population path. Preserve that URL behavior. Photo extraction should use the review/apply adapter directly without invoking automatic blank-field population. Neither extracting nor applying saves an ingredient, creates stock, creates a purchase, or publishes anything to a shared catalog.

## Extraction service and estimated cost

Propose Gemini `gemini-3-flash-preview` through Netlify AI Gateway, reusing the existing Google SDK and receipt-image processing approach but with a separate package schema and endpoint. This model is already used for receipt reading. No model change or AI release-control change is proposed for existing features.

[Google's published standard pricing](https://ai.google.dev/gemini-api/docs/pricing#gemini-3-flash-preview) is $0.50 per million text/image input tokens and $3.00 per million output tokens, including thinking. For a typical 1–4-photo import budgeted at 4,000–12,000 input and 1,000–3,000 output tokens, estimate **$0.005–$0.015 per extraction**. Example: 8,000 input plus 2,000 output is $0.010. This is a planning estimate, not a measured image benchmark or fixed price; image resolution, thinking, unreadable text, and explicit retries affect usage. A retry incurs another call. Do not add web grounding or hidden fallback calls.

[Netlify's pricing](https://docs.netlify.com/manage/accounts-and-billing/billing/billing-for-credit-based-plans/pricing-for-ai-features) currently converts $1 of model use to 180 credits: roughly 0.9–2.7 credits for the estimated import. Function/request and any explicit saved-image storage usage are additional. Record token counts and request status without recording image contents; enforce daily account limits and one active import. Confirm measured cost, gateway availability, and latency with consented test packages before enabling it for users.

## Existing fields that can be populated

| Visible package information                   | Existing draft target and safeguards                                                                                                                                                                                                                                                                       |
| --------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Product name, brand, explicit variety         | `name`, `brand`, `variant`; retain manual conflicts for approval.                                                                                                                                                                                                                                          |
| Printed barcode                               | `barcode` and known `barcodeFormat`; preserve zeros, validate check digits/formats, and show unreadable digits as uncertain rather than completing them.                                                                                                                                                   |
| Full ingredient/subingredient wording         | `subingredients`; retain full wording and parentheses. Never infer missing ingredients.                                                                                                                                                                                                                    |
| Contains statement                            | `sourceContains`, separate from advisory text.                                                                                                                                                                                                                                                             |
| May contain / facility statement              | `sourceMayContain`, preserving the actual wording. No absent statement means allergen-free. Do not automatically approve the existing reviewed-allergen checklist.                                                                                                                                         |
| Explicit net contents and multipack count     | `packageSize`, `purchaseQuantity`/`purchaseUnit`, `packCount`; keep quantity/unit paired. Use the existing package draft adapter only for supported same-category or explicitly verified conversions. Never use serving size or infer density. Preserve the canonical stock unit and existing conversions. |
| Explicit dimensions or material specification | Existing `dimensions`, `itemsPerPackage` or supported material fields when applicable; do not put supplies into food-only statement fields.                                                                                                                                                                |

The model should not populate purchase price, taxes, shipping, vendor, stock, reorder settings, recipe units, or conversions from product-label inference. A store label is not a confirmed purchase. No source webpage URL should be invented for a photo.

**Nutrition has no structured storage today.** The ingredient update allowlist, product-import schema, database model, and app source contain no supported nutrient/serving-basis record or recipe-nutrition calculation. For this phase, do not map nutrition into ingredient fields or imply it has been saved. A visible Nutrition Facts panel may help identify the photographed side, but its nutrients remain outside import. Structured nutrients, basis/units, serving count, provenance, and any calculations need a separate approved design; do not hide them in notes as a substitute.

## Uncertainty and conflicting photos

Require a strict extraction schema with field value, source photo ID/side, quoted visible text, and an evidence region where available. Treat image text as untrusted source data, never instructions. Return missing/unreadable fields as unknown, not empty-string replacements or invented values. A model confidence score is a review aid, not evidence of correctness.

Show Needs review beside unclear wording, with the relevant photo preview and both alternatives where photos disagree. Do not concatenate conflicting ingredients or choose the front over the back automatically. Conflicting barcodes/package sizes suggest different products; require the user to resolve or remove the mismatched photo before applying dependent package fields. Keep manual text editable and compare with the latest draft again at Apply time so edits made during extraction survive. If declarations change, leave their existing review status unapproved until the user reviews them.

## Phone images, privacy and deletion

The current ingredient photo uploader supports PNG/JPEG/WebP under 5 MB and up to 40 megapixels. It stores original bytes immediately as a private graphic asset; the ingredient association is saved later. It does not provide this proposal's transient extraction lifecycle or an established automatic deletion policy. Do not silently reuse that permanent-upload route for reading package photos.

Propose JPEG, PNG and WebP for the initial reader. Use camera/gallery inputs without promising browser permission bypass. Honor EXIF orientation in the preview, provide explicit quarter-turn rotation, normalize orientation on the server, strip location/device metadata, and downsample while keeping small print readable. Validate decoded MIME, pixel limits, dimensions and total request size server-side. Budget at most four prepared images with a 4 MiB aggregate payload to remain within function request limits. Reject SVG, PDF, animated formats, corrupt files and excessive dimensions with an inline recovery message. Do not claim HEIC/HEIF support until conversion is tested on the deployed decoder; unsupported iPhone images need an actionable JPEG export/retake option. Client preparation should handle large phone originals when the browser can decode them; otherwise preserve the draft and explain the limit.

For reading, retain selected images only as transient browser File objects and request buffers; do not write originals or extraction text into a persistent application cache. Revoke preview URLs on Remove/Replace/Cancel/unmount. Request completion releases server buffers; no app-side stored original exists to delete. Do not log raw image bytes, OCR text or base64. Send images only to the authenticated server and the stated AI service, with no public image URLs.

[Netlify's privacy documentation](https://docs.netlify.com/build/build-with-ai/security-and-privacy-for-ai-features) says AI Gateway does not store input/output content and providers may not use inputs to train models; request metadata is retained. [Google's paid-service terms](https://ai.google.dev/gemini-api/terms#data-use-paid) describe limited abuse-monitoring logs, and [its usage policy](https://ai.google.dev/gemini-api/docs/usage-policies#how-we-handle-data) describes 55-day retention for abuse prevention. The exact contract for the gateway route should be confirmed before release. Removing a photo in Cottage Pantry cannot promise immediate deletion of provider abuse-monitoring records. Do not use an unpaid consumer AI endpoint or claim zero retention.

Do not attach an extraction image as the ingredient image by default. If the user explicitly chooses Keep as ingredient photo, use a separately approved private-asset action, show whether it replaces the current draft image, and retain the old saved asset. Any persistent image must use Netlify Blobs, tenant-scoped metadata and authorized reads, with explicit deletion that checks references; no shared catalog publication. The smallest first phase can omit Keep entirely and preserve the existing image picker/upload unchanged.

## Implementation and verification after approval

Add one authenticated package-extraction operation, bounded payload/model schema, transactional account usage counters in Netlify Database, and no image persistence for extraction. Add the compact inputs/review adapter to both Add and Edit Ingredient. Do not enable unrelated assistant/recipe AI or change subscription behavior.

Test front-only, back-only, multiple close-ups, rotation, large/unsupported phone files, unreadable text, mismatched packages, provider failures/retry, in-flight manual edits, checkbox conflict protection, full statements and Contains/advisory separation, cancel/removal, preserved chosen images, and account isolation. Assert that extraction/apply causes no ingredient save, stock change or catalog publication. Re-run the existing URL/barcode checks and capture actual desktop/mobile screenshots after implementation. Those photo-specific results and a measured per-import cost are still pending.
