# Barcode lookup and shared catalog proposal

Approved by the user on November 7, 2026 as a phased plan. The approved workflows were implemented; see [implementation and actual verification](catalog-and-photo-implementation.md) for provider setup, rollout and limitations. This document records the approved design. Package-photo extraction is a separate [proposal](package-photo-import-proposal.md). Category recovery is documented [separately](category-load-recovery.md).

## Reuse the existing workflow

Add Ingredient already keeps URL, Barcode, and manual fields in one Details section and one draft. `ProductLinkImport` provides the compact checkbox review, field conflicts, Select all/Clear, inline full-text expansion, source metadata, and approved photo attachment. Its current URL mode also fills certain blank fields immediately; preserve that working behavior. New catalog/provider results should wait for Apply selected values.

`InventoryBarcodeReview` already searches private inventory, including purchase-offer barcodes, and offers View Item. Keyboard Enter prevents form submission. `BarcodeScanner` uses the browser detector with ZXing fallback, handles camera permissions, and stops after an accepted scan. Reuse those paths and add a shared in-flight lookup guard for repeated scans, cancellation, and late responses. No lookup should enter receiving or purchasing.

Packaging and consumable supplies already use the private `ingredients` table with `usedAs: packaging` / `supply` and stable `categoryId` values. They are not a new food-ingredient database. Existing product metadata includes variants, dimensions, material composition, and pack counts; food-only statements are gated by `foodProduct`. Preserve these adapters and private stock/cost behavior. There is no shared ingredient/supply reference catalog today. The billing catalog is unrelated.

## One lookup sequence and draft

Keep URL and Barcode at the top of Details; add a small Search catalog control in that area, followed by the same manual fields. No entry-method tabs or large instruction panels. Results, retries, source links, and review stay inside the popup at desktop and phone widths.

1. Search the selected account's existing ingredient, packaging, supply, and package-offer identifiers. An existing match says Already in your account and offers Open existing item. Retain the unfinished draft in the parent editor while switching to the existing-item view, with Return to draft; do not discard it through route navigation or create a duplicate. Do not persist business drafts to browser storage.
2. Search approved shared catalog identifiers, or search shared names/brands when the user chooses that control. Return all ambiguous package variants for review.
3. For food, query USDA FoodData Central through a server provider adapter. Check each returned `gtinUpc` against the submitted barcode; keyword relevance alone is not confirmation. Generic food search results cannot become exact branded matches. For packaging/supplies, report that the initial external food provider does not cover them and offer internet search. A commercial non-food provider can be added later after its redistribution rights and cost are approved.
4. On no useful match, offer an explicit Search the internet action using the exact barcode. Display title, domain, and source link; distinguish a confirmed identifier in product data from an unverified search candidate. The user selects a page before invoking the existing URL importer. A search snippet is never an ingredient statement. Preserve a selected unsupported page's source link in the draft and allow manual completion.
5. Keep manual entry available during no results, provider failures, rate limits, cancellation, or unsupported pages. Late results must not overwrite a newer draft or query.

Store raw barcodes as strings. Preserve leading zeros and validate supported numeric GTIN lengths and check digits without repairing missing digits. Reuse valid UPC-A/EAN-13 equivalence; extend valid GTIN-14 matching deliberately. Expand UPC-E only with an explicitly known scanner format. Ambiguous eight-digit input stays distinct from EAN-8. Internal QR/Code 128 identifiers use exact private matching and never become external GTIN requests. Similar names never establish duplicate package identity.

## Relationships and account boundaries

Use Netlify Database for all structured persistent records and private or separately permitted Netlify Blobs for images. Add forward migrations and matching Drizzle definitions; preserve every applied migration. Do not migrate or rewrite existing user items automatically.

Proposed reference records are `catalog_items` (stable identity/type/status), `catalog_identifiers` (raw/normalized codes and format), and immutable `catalog_revisions` (reviewed field snapshot, sources, reviewer, review scope/date, license metadata). Signed-in workspace members read approved revisions only. Only authorized platform administrators can publish; use existing platform-admin authentication and MFA enforcement. Public records contain no account prices or business links.

Add tenant-scoped `ingredient_catalog_sources` for the private item ID, accepted catalog revision, accepted fields, and source history; use the existing composite business/item foreign key plus an immutable revision reference. Keep a field snapshot in the saved private item. Private prices, vendors, recipes, taxes, shipping, stock, locations, reordering, purchase history, notes, overrides, and uploads remain behind existing membership resolution and forced RLS. The server resolves the business and role; clients cannot choose either through IDs.

`catalog_submissions` contains only an explicitly submitted allowlist snapshot and permitted image copies. Its private submission ownership uses RLS. Platform review receives that snapshot, never general access to the submitter's inventory or private asset collection. Add transactional provider-attempt counters and bounded caches in Netlify Database, with no private data in shared caches. Keep secrets server-side, validate inputs/URLs, enforce membership and write roles, and rate-limit each account plus each provider's aggregate quota. Return versioned lookup/review JSON so a future phone app can use the same service.

## Shared fields, review and updates

A generic starter item contains a type/category and generic name, with unknown fields left unknown. An exact branded entry additionally carries supported brand/variety, explicit package contents/unit, barcode identifiers, full ingredient/subingredient statement, separate Contains and advisory statements, or supply dimensions/material/pack count. Include source references, licensed images where permitted, revision history, and the exact review scope. Never invent package size, allergens, price, density, or conversions. Nutrition serving size is not package contents.

Use Draft, Pending review, Reviewed against cited source, Needs review, Withdrawn, and Superseded states. Reviewed means the named fields were compared with the cited package/source on the stated date; it is not laboratory verification, allergen-free certification, or a guarantee that a package has not changed. Missing allergy data remains unknown.

Add to my ingredients/supplies opens the existing editable draft and compact checklist: usable empty fields preselected, differing nonempty values unchecked with both values visible, unchecked fields unchanged, Select all/Clear and one Apply selected values action. Preserve long text through inline expansion. Statements remain separated, chosen images are never replaced implicitly, and source provenance is accepted with the selected values. Only explicit Save creates the private item; it creates no stock, purchase, or adjustment.

Initially administrators manage the catalog. Users may explicitly submit a new product/correction after seeing exactly which fields and image copies would become shared and confirming reuse rights. They cannot publish or edit everyone's record directly. Deduplicate submissions by valid identifier, item type, brand/variant and package details; route matching proposals to a revision of the existing item. Conflicting identifiers and package sizes require administrator resolution, never automatic merging.

Approved corrections create new immutable revisions. Private records retain their accepted revision, values, costs, ingredient statements, and overrides. Offer Catalog update available with field-level differences and selected acceptance. Withdrawn or obsolete variants remain addressable for saved references/history but are excluded from ordinary new selections; show replacements as suggestions. Withdrawing a shared image stops new use, with a separate dependency-aware review before removing any already accepted private copy. Do not delete historical links.

## Phases and acceptance

1. After approval, add the reference schema, access policies, immutable revisions and admin-only catalog management. Curate a small generic ingredient/packaging/supply starter set without fabricating branded data.
2. Add private-first barcode and shared name/brand lookup using the existing scanner, review component, and shared draft; add explicit private source links and no-stock saving. Test leading zeros, variants, Enter suffixes, duplicate scans, draft return, and cross-account denial.
3. Add FDC lookup and SerpApi fallback after their actual setup/terms checks. Test exact versus candidate matches, external-source review, no results, unsupported pages, provider errors/timeouts/429s, retries, and manual/URL/barcode regressions.
4. Add contribution review and optional catalog-update diffs. Test duplicate submissions, publication boundaries, immutable accepted history, withdrawn variants, and preservation of all private values and uploads.

Acceptance covers all thirteen requested cases, including full ingredient text, separate allergen/advisory statements, no silent changes to private records or stock, and compact desktop/phone rendering. Capture actual synthetic-data screenshots after implementation; clearly separate fixture checks, real tenant-scoped database tests, and authenticated deployment checks. Actual implementation coverage and test results are recorded in the separate implementation report. Recipes, costing, inventory transaction rules, labels, Square, billing, and subscription tiers remain outside this proposal.
