# Product category dropdown verification

The product selector fetched `/api/workspace?productCategories=1`. The authenticated workspace handler loaded the current business's settings and returned `settings.productCategories`; this is separate from pantry categories. The response parser accepted optional section scopes. The selector then required `category.scope === productCategoryScope(product)`, retaining only the currently assigned category as an exception. This hid otherwise valid older categories without a scope from creation and from alternative selections during editing. The product write validator also rejected newly selected unscoped IDs. Existing fixtures explicitly represented this older storage format, and isolated browser coverage exercised those previously excluded records after the compatibility correction.

A shared product-category eligibility predicate now accepts the existing shared, unscoped product list as well as the matching explicit product section. Both the selector and product write validation use it. Explicitly scoped categories remain restricted to their sections; inactive categories cannot receive new assignments. The category response parser, business query, verified ownership, roles, row policies, and tax matching were retained. Category IDs remain the saved values, with category names and existing classification annotations displayed. No category definitions, product assignments, classifications, migrations, or real business records were rewritten.

The selector retains its loading status, retryable failure message and disabled state until a successful fetch. Its empty message now means no active eligible categories. Existing saved labels remain visible during a fetch using the already-loaded workspace configuration. Inactive, missing and other-section saved assignments are explicitly explained and retained. Category creation updates the fetched configuration and selected ID; management-dialog close refreshes the list.

The browser fixture mounted the actual workspace application through the local Netlify development origin at `http://localhost:8889/capture-fixture`. It intercepted all workspace requests with synthetic demo records, including synthetic save and reload responses; no customer account or production data was used. Local browser save/reload verification is complemented by the isolated PGlite tests of the real workspace handler, permissions, tenant separation and persistence. It is not a deployed preview or an end-to-end check against a remote database.
