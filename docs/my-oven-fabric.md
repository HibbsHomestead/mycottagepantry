# My Oven and fabric yardage

The customer application was named My Oven. Cottage Pantry branding and the nine existing section names were retained. `/oven` became the application route and `/oven/billing` became the account billing route. Server-rendered application metadata used `My Oven | Cottage Pantry`; active sections/tabs used `[Section] | My Oven | Cottage Pantry`.

## Routes and access

Hosting redirects and client-routing fallbacks retained `/workspace`, `/workspace/billing`, and `/studio`. No `/studio` implementation was found in the prior source; an alias was nevertheless supplied for previously shared links. Redirects retained query strings and browser fragments. Existing hashes were then resolved through the existing section mapping, so `/workspace#Pantry/Vendors` opened `/oven#Purchasing/Suppliers`, rather than Dashboard. Internal entry, settings, support, and account links were updated. Back/Forward and the existing unsaved-edit guards were retained.

Login return validation previously accepted only a small list of top-level section hashes and rejected tab paths. It was extended to current sections/tabs, existing legacy hashes, and search/filter state. Multiple-business selection retained the requested section. Return URLs remained same-origin and restricted to application destinations. Identity callback handoff retained the existing fragment and query rather than discarding the query.

`accessTrace` was an existing UUID correlation identifier for account-access diagnostics. The client supplied it as `X-Access-Trace`; the account-access response and sanitized diagnostic events used it to connect login, session verification, membership lookup and navigation. It did not authorize access. UUID validation and fresh random generation were retained, and navigation preserved the reference. No example identifier was added to application code. The existing temporary `__app_update` query parameter remained supported.

The audit found no web manifest, service-worker registration, live invitation administration, or live payment/integration return implementation to migrate. Identity verification/recovery callbacks still handed off to login. Invitation callbacks continued to explain that application invitation acceptance was unavailable. The existing Square Sandbox webhooks and provider verification endpoints were unchanged. Billing aliases retained provider query parameters, but live provider returns and actual email delivery were not verified.

## Fabric records and calculations

Fabric used the existing tenant-owned `ingredients` craft-material records, recipes/designs, batches, immutable stock ledger, journals and receipt matching. No additional inventory system was created. Optional fabric metadata used the existing JSON fields: `materialType`, `fabricTracking`, `fabricWidth`, `widthUnit`, `fiber`, `color`, `pattern`, `collection`, `pieceMode`, `pieceId`, `pieceLength`, `pieceLengthUnit`, and the existing photo, SKU/barcode, supplier, location, notes and reorder fields. Remnant transfers recorded a server-created parent reference. Different widths, colors and prints were separate records.

Yards, feet, inches, meters and centimeters used the existing exact unit factors. Fractions and mixed fractions were parsed before calculation. Length, count, area, weight and volume were kept distinct. Fabric rejected ingredient-style contextual cross-category conversions. Width stayed separate from stock length. Design material lines supported an optional minimum width, checked both when saving a design and when completing production.

Fabric retained its chosen stock/display unit. Normalized numeric quantities and unit costs were saved without display rounding in the existing JSON records, alongside the existing `numeric(20,8)` stock/cost columns. Reopening read the saved calculation values. Display formatting was separate and used up to eight fractional digits. Calculations used standard JavaScript numeric precision; arbitrary-precision rational arithmetic was not introduced. Existing ingredient and packaging conversions were unchanged.

Direct purchases accepted a total acquisition cost or a price per selected purchase unit. Total cost was divided by confirmed stock quantity; subsequent receipts used the existing weighted-average policy and Inventory asset / Cash journal. Bolt/roll receipts required an explicit usable length per purchased bolt/roll and owner confirmation for every receipt. No package length was inferred. Receipt review could match existing fabric records, receive compatible length or confirmed bolts/rolls, and retain the existing tax/charge allocation policy. Different widths and separate pieces needed their own fabric record before matching. Creating fully described fabric directly inside receipt review was not added.

Precuts, fat quarters and bundles were tracked as counted `each` records, optionally with piece dimensions. They could not be received or consumed as continuous yardage. A counted bundle represented the owner's selected inventory item; no bundle-to-piece contents were inferred.

Design and production forms showed planned use, available stock, estimated input cost, shortages and width problems. Completion deducted actual material use plus separately entered waste, received good finished output, and locked the cost basis and actual usage. Existing batch completion fingerprints prevented repeat deductions. Unused fabric remained on hand rather than becoming automatic waste.

## Pieces and remnants

Owners could choose total length with unknown continuity or one separate piece per record. Separate pieces displayed their identifiers, lengths, widths and locations and could be selected individually in a design. New receipts could not merge additional material into a nonempty separate-piece record. Two half-yard records remained two selectable pieces, not one continuous yard.

A usable-remnant action transferred length from a parent record to a new separate-piece record at the same width and unit cost. Both movements were written in the same business transaction. The parent's balance fell by exactly the child's opening balance, so total stock and value did not increase. Stable request IDs and payload fingerprints prevented duplicate transfers and rejected reuse with different values. Transfers did not create a second purchase or a waste charge.

Automatic cut layout, automatic allocation across multiple physical pieces, and narrower-width cut-remnant geometry were not implemented. Full-width remnant transfers and separate piece records were supported. The interface disclosed that total yardage did not establish a continuous piece. Existing untyped craft records and historical transactions were not reclassified.

## Storage, access and recovery

No schema migration was required: the existing JSON metadata and stock columns supported the extension. All 16 applied migrations were left unchanged. No production business records were modified during this work. Existing tenant ownership, RLS, ledger balance constraints, accounting triggers and role checks were reused. Material edits preserved quantities and costs; width, tracking method and stock unit were fixed after creation. A different width or tracking method required a separate record.

Fabric metadata edits followed existing ingredient-edit access; remnant transfers followed existing adjustment entitlements and additionally required Owner/Manager access. New material/remnant records counted against the existing stock-record quota. No billing assignment, paid access, tax category, or subscription limit was changed. Standard source rollback remained possible without a data migration; fabric metadata and ledger history would remain stored and older craft stock records would not be removed.
