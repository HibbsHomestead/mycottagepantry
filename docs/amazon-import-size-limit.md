# Amazon product import: bounded page-size repair

The exact owner URL was `https://www.amazon.com/dp/B0FK3XFMQQ?ref_=ppx_hzsearch_conn_dt_b_fed_asin_title_4`. Public retrieval returned HTTP 200 and 1,682,604 response-body bytes, exceeding the old application limit of 1,048,576 bytes. A separate response from the same URL was 1,115,108 bytes; retailer responses varied. Both exceeded the old threshold. The observed document identified Roppolo 100-item bread bags and contained the matching selected ASIN, product title, product overview, and product image. No challenge or sign-in page was detected in those observations. These were observations from this environment, not a guarantee of what Amazon returns to every request.

The old cap was hard-coded in `fetchRecipeUrl` in `netlify/lib/recipe-import.ts`. `fetchProductDetails` reused it and changed “recipe” to “product” in the error. It counted native HTTPS response body chunks before UTF-8 decoding. HTTP transfer framing had already been removed, but content compression was not explicitly decoded. The request asked for identity encoding. If a server nevertheless sent compressed content, the old counter measured encoded bytes, rather than enforcing a decompressed-content cap. Content-Length did not drive that old check. This was an application download limit, independent of platform invocation payload limits, billing, AI credits, structured-data extraction, and retailer access denial. No AI or paid extraction service was used for this import.

The revised product HTML limit was 4 MiB (4,194,304 bytes), with independent counters for downloaded and decompressed content. Recipe and remote-photo downloads retained their 1 MiB caps. The product cap provided approximately 2.5 times the largest observed document size. The native fetcher supported bounded gzip, deflate, and Brotli decoding; rejected unsupported or corrupt encodings, incomplete bodies, and inconsistent declared lengths; and stopped oversized streams without returning a product prefix. Missing or misleading Content-Length could not disable either byte counter. Complete bounded HTML with a missing Content-Type was recognized only by an explicit document prefix; image fallback used known raster signatures. Declared unsupported types were still rejected, and the upload pipeline still validated actual raster data.

The existing 12-second fetch budget, up-to-four-second DNS lookup deadline, three-redirect limit, HTTPS-only public-address validation, DNS pinning, mixed-public/private DNS rejection, and redirect revalidation were retained. DNS waits also respected the remaining overall budget. Account cookies and authorization were not sent to retailers. No access restriction was bypassed, and scripts were not stripped to make the download fit.

Memory work reused the already parsed HTML document for ingredient-statement extraction. The final exact-URL secure-fetch observation at 2026-11-02 03:20:15 UTC completed retrieval and extraction in 306 ms with a process RSS increase of 92,770,304 bytes (about 88 MiB), and again measured 1,682,604 bytes. This was a local measurement, not a hosted peak-memory guarantee. A 4 MiB input limit, one shared page DOM, bounded decompression, and the fixed fetch deadline provided conservative headroom within the standard 1 GiB function runtime without raising function memory or introducing inference charges. DOM memory depends on document structure; the cap was not presented as a formal heap bound.

The larger page also lacked Product JSON-LD. A separate, narrowly scoped Amazon adapter read only an exact ASIN-matched product title, image, overview brand, explicit Number of Items, and an unambiguous primary pay price when present. It excluded unit, list, recommendation, installment, and conflicting offer prices. Bag capacity and item weight were not treated as purchase quantity. Currency was not inferred from a dollar sign or hostname. The recorded secure-fetch observation imported the name, brand, ASIN, 100 each, and image; its primary price was unavailable, so manual pricing remained necessary. Synthetic source tests exercised available primary prices and conflicting or missing prices separately.

A visible “Paste product text” action opened a notes field in the existing ingredient/packaging draft. It explained that pasted text was reference notes and that name, package, and price were entered in the form. It did not claim automatic pasted-text extraction. Import failure, note editing, and retry preserved the open draft. Saving stayed separate from applying suggestions. No refresh recovery or login-session change was introduced.

Validation included complete valid HTML below and above 1 MiB; rejection above 4 MiB; missing, invalid, understated, and overstated Content-Length; compressed expansion above the decoded cap; malformed compression and interrupted streams; timeouts before headers and during an unfinished body; redirects and SSRF boundaries; and sign-in, challenge, and generic non-product documents. An opt-in live test retrieved the exact URL through the actual bounded fetcher. A separate opt-in API test used that live source, fetched its available image, and saved/reopened its name and package metadata in disposable PostgreSQL with a manually confirmed synthetic purchase price where the page omitted a price. Identity and photo-object storage were test adapters; customer accounts and the production database were not written. Synthetic browser checks covered review/apply, image handling, save failure/retry, reopening, refresh, and the existing Packaging behavior.
