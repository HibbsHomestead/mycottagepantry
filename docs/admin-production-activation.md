# Production authentication verification

Publish authentication changes through the managed source review and production workflow. Do not deploy a local build over production or activate live checkout as part of an authentication release. Preserve every applied database migration and apply the new forward migration with the release.

After the release is published, record its actual commit, deployment ID and observation time. On desktop, phone and tablet, verify password sign-in, password recovery, sign-out and session expiry without any device-credential prompt. Use an existing administrator account privately; never put a password, setup key, recovery code or cookie in a report.

In the sensitive-action panel, verify an enrolled authenticator or single-use recovery code. For an administrator without an enrolled authenticator, verify the password again. Confirm that billing credential controls reach their real validation requirements after verification. Before verification, direct sensitive-action requests must remain forbidden; logged-out, revoked, expired and cross-origin requests must remain rejected. Verify that the retired enrollment/assertion actions are unavailable to signed-in callers as well.

For a former passkey-only account, verify password confirmation and optional authenticator enrollment without the old credential, including accounts with expired historical enrollment deadlines. Confirm the new authenticator code before treating enrollment as complete. Other sessions must be revoked, and used codes must not replay. Enrolled authenticator accounts must not gain sensitive-action access using password confirmation alone.

No authentication-provider passkey setting is required by this application: the retired second factors were application-managed public-key credentials. An account holder who needs a password uses the existing Identity recovery email. If Identity cannot deliver that email, an authorized project owner must inspect **Project configuration → Identity → Emails** and its configured SMTP delivery, plus the account's confirmed/invited state in **Identity → Users**. Resolve delivery or resend the pending invitation there; do not request secrets in chat or change administrator grants as a workaround. This is conditional troubleshooting, not a required setup change for every account.

Password-recovery tests and source regressions are not production acceptance. Successful production password confirmation, enrolled-code verification and protected billing access require an authorized private account session. The execution service creates the source commit/review after the coding run, so a report prepared before that publication must explicitly mark the new deployment and authenticated production checks pending.
