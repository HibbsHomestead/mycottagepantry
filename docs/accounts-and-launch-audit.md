# Accounts, workspaces and public launch audit

This is a source audit and proposed implementation plan, not authorization to open registration. Existing owner records, authentication provider, roles and subscriptions were not migrated. No production data writes or signup/email tests were performed. The public website now has separate routes; the application is at `/workspace` with a server-checked Identity entry. The API independently establishes ownership. Site protection is an additional deployment layer, not application login.

### Evidence and limits

The existing published site's root and Identity settings endpoints returned HTTP 401 HTML from site protection during the earlier read-only audit. Current verification/autoconfirm/registration, SMTP sender/reply, active provider subscriptions and production-domain link configuration remain unverified. No account credentials or token values were inspected or returned. Preview database inspection was unavailable. Source shows isolation defenses, but **no real two-tenant database/RLS, session revocation, email delivery or custom-domain recovery/invitation test has passed in this audit**. Existing backend tests mock DB, Identity and provider responses. A successful build cannot establish those properties.

Public pages do not call the workspace API. `/workspace` checks the existing Identity session before rendering the application. Existing API demo provisioning remains in source and is not a public signup model; direct unauthenticated API access still uses isolated browser-demo behavior and requires an explicit/rate-limited demo design before public release. No changes here grant one user another user's records.

## Proposed account model — review before migrations

Keep these records distinct:

- **Managed identity/global user:** stable provider identity ID, display name, verified-email state, profile preferences. Credentials remain with Identity; no custom password hashes.
- **Workspace:** business name, currency, IANA timezone, lifecycle and onboarding state. Existing owner workspace IDs and all records remain unchanged.
- **Membership:** workspace ID + global user ID, active status, role, accepted invitation reference and timestamps. Unique membership pair supports multiple memberships later. The initial app may choose a deterministic home membership without a workspace switcher.
- **Workspace subscription:** billing customer/provider IDs, approved plan/version, status and period/trial dates. Separate entitlements/limits snapshots and usage counters. No role is inferred from payment status.
- **Legal acceptance:** user/workspace, Terms version, Privacy version, server timestamp and acceptance source. Marketing consent is a distinct optional record, never a condition of account access.

A verified **new-business intent** creates exactly one empty workspace and Owner membership in one idempotent, locked transaction. Uniquely key the onboarding intent/creator and retry the read of its committed result. Redirects, refreshes and repeated clicks must return the same workspace. Do not seed customer records, stock, sales or opening balances. Preserve existing membership before considering provisioning. An inactive membership is denied, not auto-provisioned.

An invitation is a different intent: validate its workspace, verified intended recipient, expiry, revocation and single-use state first. Accept an existing account into that workspace. Never create a new workspace when an invite is invalid, expired, already accepted or retried. Store a hash of a cryptographically random token, never its plaintext in logs. Deduplicate pending invites per workspace/email; resend revokes the old token. Acceptance, membership insertion and token consumption are one transaction. Removed members lose API, file and job access regardless of browser state.

Onboarding collects name, email, managed authentication, verification, versioned Terms/Privacy acceptance, workspace name, currency and timezone. Support safe repeat signup, verification resend, expired links, recovery, email changes requiring provider verification, logout and session expiry with accessible, generic messages. Avoid revealing whether an email already exists. Provider-sent mail must not be duplicated.

Prevent demotion/removal of the last active Owner transactionally. Ownership transfer requires current Owner reauthentication, verified receiving identity, explicit acceptance and an audited atomic transition. Workspace membership and operation permission precede every entitlement decision. Verify both sides of JSON-linked records and normalized links. Jobs need workspace/actor identity and reauthorization at execution, no implicit privileged cross-tenant worker. Cache keys include workspace and authorization scope; private downloads are reauthorized and no-store.

The current commercial direction is proposed Free plus Mixing Bowl ($10), Baker’s Bench ($25) and Cottage Kitchen ($40), monthly per business workspace. Mixing Bowl includes the full solo-business core; no small paid catalog limits are proposed. See [revised subscription proposal](subscription-proposal.md). No launch trial or active restrictions are enabled.

## Phased delivery

1. **Authentication and tenant isolation:** review provider settings; reject inactive memberships; separate explicit demo provisioning; sanitize errors; cover business RLS and cross-record links; reauthorize after external waits; test real two-tenant DB/files/exports/cache/revocation. Preserve owner data and review migration/backfill before applying.
2. **Signup/onboarding and recovery:** idempotent empty workspace + Owner; verified minimal onboarding and legal acceptance; provider settings-driven closed/open registration; resend/recovery/email-change and expired-link UX; correct production links and abuse limits. No public registration until phase gates pass.
3. **Roles and invitations:** approve matrix/mapping; scoped reads and exports; owner-authorized single-use invites, revocation, existing-account acceptance; last Owner and transfer; removed-member backend tests. Cottage Kitchen remains unreleasable until complete.
4. **Subscription readiness:** approve draft prices and lifecycle, server-owned subscription/entitlement storage, webhook signature/idempotency, all-operation enforcement, seat counting including Owner, usage separation, billing portal and transactional notices. No billing products or charges until explicit approval.
5. **Invite-only beta and launch checks:** owner invites a small reviewed cohort; verify delivered email and domain links with approval, restore practice, responsive/accessibility checks, privacy/retention/support processes, operational monitoring and costs. Review before opening public signup or checkout.
