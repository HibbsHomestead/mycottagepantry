Authenticated administrators now have **Admin sign-in security** below the page heading. **Set up authenticator app** prepares a short-lived, operation-bound authentication challenge; a separate **Verify existing phone passkey** click calls WebAuthn directly. Only a successful user-verified assertion from an already enrolled credential can create the five-minute pending setup. The encrypted pending secret is bound to that session. The user scans a locally generated QR or enters the setup key in an authenticator app and submits its first six-digit code before activation. Setup cancellation clears pending provisioning; closing the page without confirming never activates the method. Setup secrets and recovery codes are handled only in the authorized no-store response and ephemeral UI state, never browser persistence, audit payloads, or logs.

AES-256-GCM encryption binds each secret to its identity with authenticated associated data and a random nonce. Secrets use 160 bits of cryptographic randomness. Six-digit SHA1 TOTP uses 30-second periods and a one-step skew window. The accepted highest time step is stored under transaction locks so confirmation codes and subsequent accepted codes cannot be reused, including concurrent requests across sessions. Code attempts share a committed per-account limit of ten per ten minutes, plus per-IP limits, independent of transaction failure and login-session replacement. Confirmation consumes its step; the user may need to wait for the next app code to sign in on the computer.

Activation returns ten high-entropy single-use recovery codes once. Only identity-bound SHA256 digests are stored; raw codes are never recoverable from the database. Each requires a password-verified administrator session, and atomic consumption prevents concurrent reuse. Recovery establishes a normal bounded administrator session without deleting the phone passkey or reopening passkey enrollment. Recovery-code replacement and authenticator removal each require a fresh operation-bound existing-passkey assertion. Removal deletes the authenticator/recovery records, signs out other administrator sessions, and preserves the freshly verified phone session and phone credential. Audit writes cover setup, confirmation/activation, verification, recovery, replacement, cancellation, removal, and denied attempts. Audit failure rolls back activation and code generation.

Once the server reports confirmed enrollment, password-verified sessions show **Sign in with passkey** and **Sign in with password + authenticator code**. The latter uses a normal form and does not invoke WebAuthn or Windows Security. Invalid-code responses clear the input and leave retry enabled. Codes are not offered for unconfirmed enrollment. Password alone still cannot load protected admin data. TOTP is less phishing-resistant than passkeys, so the working phone passkey remains the preferred factor for security settings.
