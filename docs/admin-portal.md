## Architecture and authorization

The project serves the administration surface on its dedicated subdomain through a host router. The admin host exposes only the admin page, admin API and necessary public assets. It does not serve `/oven`, customer APIs, or public Identity authentication routes. The customer hostname retains its existing routes; its `/admin` entry redirects to the admin subdomain. Navigation uses meaningful section queries, preserves customer search and pagination, and supports refresh and browser history.

Every administration API request checks an exact allowed origin and a custom request header. Production uses the dedicated HTTPS admin origin. Preview access is limited to the platform-configured URL for that preview; local emulation uses port 8889. Cross-origin and sibling-subdomain requests are rejected, with no permissive CORS response. POST requests additionally require JSON and the matching Origin header.

Password verification uses the existing Identity SDK on the server. Provider tokens are removed from the admin host's cookies after verification. The application issues a separate random, host-only `__Host-` cookie with HttpOnly, Secure and SameSite=Strict attributes. Only its hash is stored in Netlify Database. Pending MFA sessions last five minutes; verified sessions last thirty minutes and are rotated after MFA. No authentication cookies are shared across subdomains, and customer login behavior was not replaced.

Platform permission comes from an explicit server-managed administrator record keyed by immutable Identity ID, independent of customer owner/team roles and browser state. Each request rechecks the current provider identity, enabled grant, grant epoch, origin, expiry and MFA state. Provider failure fails closed. Permission changes invalidate existing sessions through the epoch. The interface also rechecks its session periodically and clears displayed data on an authorization failure.

WebAuthn requires user verification, with challenges bound to the administrator session, exact origin and RP hostname. Challenges expire after two minutes and are consumed even on invalid verification. Authentication checks the registered public key and updates its counter. First-device enrollment is allowed only in the explicitly granted enrollment window. There is no public signup-to-admin, email allowlist, first-registration grant, browser admin flag, or self-service recovery bypass.

Login, MFA and gateway limits persist in Netlify Database, including failed attempts. Login limits apply to both the verified runtime IP and a hash of the normalized account input; browser forwarding headers do not establish the IP. Authentication and data access outcomes are audited without credentials, raw errors or request bodies. The audit is append-only, and the database prevents removing the last enabled platform owner. There are no business-data exports, customer file viewers, impersonation, account restrictions or destructive controls in this release.

The project owner explicitly confirmed the existing provider-verified Identity account `8a87b82e-1393-4c4d-9885-62f946204b6e`. A subsequent live provider lookup confirmed that account again. The additive `20261111010000_bootstrap_confirmed_platform_owner` data migration queues a grant for that exact account through the controlled deployment process, records the confirming project owner and safe before/after audit metadata, and opens a 24-hour first-device enrollment window starting when the grant is inserted. It creates no authenticated session or credential. If any administrator record already exists, including a disabled grant, it does nothing; replay cannot restore revoked access or reopen enrollment. The production deployment subsequently reported this migration as applied, and the owner reported successful production login and MFA. The stored grant and actual enrollment timestamps still require production database or authenticated audit verification; successful application alone does not prove that the guarded insert occurred.

The separate trusted-operator bootstrap utility also verifies project ownership and the immutable Identity account, requires repeated account and database-branch confirmation, and refuses to run if any administrator exists. This runner could not verify an owner-level CLI session, and that utility was **not executed**. Device recovery and subsequent administrator administration are not implemented in the UI. An expired initial enrollment window requires a separately authorized and audited operator recovery; there is no automatic extension.
