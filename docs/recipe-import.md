# Recipe import

Recipes and Quick Add both open **Import recipe**. The flow is import, extract, confirm Pantry matches, review, then approve. Pending imports are separate `recipe_imports` records in Netlify Database, with business ownership and forced row-level security. Original files and source snapshots live privately in Netlify Blobs and are served only through the authenticated workspace API.

## Supported sources

- Paste recipe text: deterministic classification of recipe metadata, required ingredients, optional additions, method sections, notes and uncertain content before ingredient quantities are parsed. Fractions, mixed numbers, groups and explicitly labeled timing are supported. No AI credentials are needed.
- Upload: PDF, JPG, PNG and UTF-8 `.txt`, up to 4 MB. Actual signatures and image decoding are checked; MIME headers alone are not trusted. Plain text is limited to 60,000 characters.
- Public HTTPS recipe/share pages: Schema.org Recipe JSON-LD is preferred, including multiple recipes in one page. Otherwise visible page text is parsed for review. Source HTML is retained as an original snapshot, served as plain text rather than executed.

CookBook Manager shared plain text has a dedicated import option; see [CookBook exports and product links](cookbook-product-import.md). No cookbook account integration or proprietary cookbook export format is currently supported. Unsupported exports are explicitly rejected. The adapter registry is ready for official providers; only enabled, working integrations should be exposed. Import is one-way. Remote recipe images are not copied without authorization; uploaded source images remain available in the source preview.

## PDF and photo reading — disabled for launch

Automatic document reading previously used the Google GenAI SDK through Netlify AI Gateway. It is retained internally, but `AI_ENABLED` defaults OFF and blocks the provider adapter before any request. PDF/image uploads retain the original and a manual-review draft with an explicit message. Paste recipe text, upload UTF-8 text, use a public recipe URL, or manually review the original instead. No alternative paid service is used. Receipt attachments similarly no longer trigger automatic OCR. No live inference was performed. Future re-enable requires separate release and usage approval; it is not included in subscriptions.

## Review and costing

Each original line, group, quantity, unit, ingredient identity and preparation descriptor can be reviewed. Lines can be added, removed, split at newlines/semicolons, or assigned to a different group. Quantity ranges remain unknown and retain their original wording. Alternative additions such as “pecans, walnuts and/or oats” stay together in a separate optional section, outside Pantry matching and required costing. A suggested exact Pantry name/alias match still requires confirmation. No fuzzy ingredient merging occurs.

**Instructions / Method** provides editable ordered steps, editable section headings, add/remove and up/down controls. Content can move between required ingredients, instructions, optional additions, notes and unclassified review text. Wrapped method paragraphs stay together. Unclassified text must be resolved before approval, and method prose cannot be approved as an ingredient. If the preserved text appears to contain directions but the method is empty, a prominent warning requires review and an explicit acknowledgment before approval.

Drafts store `instructions` and corresponding `instructionGroups`; approval serializes them into the existing canonical recipe `instructions` string. The recipe editor and detail Method section use that same field. `optionalAdditions`, `sourceUrl` and `sourceAttribution` persist separately. Source URLs do not become descriptions. Missing yield and timing remain `null`, not inferred values or zero.

US cups (236.5882365 ml) and metric cups (250 ml) require an explicit selection. Metric cups are stored as their confirmed volume in ml; original text and cup standard are retained. Ounces and fluid ounces remain distinct. Package/case contents and ingredient-specific volume/weight relationships are never guessed. Verified conversions use the existing conversion service; the import conversion form starts with a blank destination amount.

Incomplete imports can be saved without creating recipes. Approval requires a title, positive yield, yield unit, positive quantities, known units, and confirmed Pantry/new-item decisions. Missing conversions or purchase prices remain flagged as **Cost incomplete** in the review and recipe costing. An absent price is distinguished from an explicitly entered zero price. Production calculations cannot silently use a partial total. New Pantry ingredients require explicit approval, start at zero stock with unknown purchase/reference cost and unreviewed allergens, and create no purchase or opening balance. The database's required zero numeric valuation for an empty new stock record is not presented as a known ingredient price.

Imported prep/cook times remain distinct from costing labor. Imported recipes start with zero allocated labor and overhead; users configure costing separately. Import does not create products, batches, sales, purchases, stock movements or journals. Label ingredient order still follows existing weight-based logic and reviewed Pantry declarations.

## Duplicates, approval and safety

Duplicate checks use source identifiers, canonical source URLs, source-file hashes, and title similarity. Users can open an existing recipe, import a copy, or review a new version. A reviewed version creates a new recipe linked to the original; it does not silently change existing product links, recipes, historical batches or costs.

Approval holds the workspace database lock and atomically writes approved Pantry additions, recipe, relational recipe lines, provenance and audit entry. The stored import-to-recipe link makes repeated approvals idempotent. Concurrent draft edits are checked against the saved revision. Cancelled imports retain source history and cannot be approved. Closing with unsaved edits requires a discard decision.

URL fetching uses native HTTPS with validated, pinned public DNS addresses. Every redirect is revalidated. Private/reserved addresses, embedded credentials, custom ports and non-HTTPS schemes are rejected. Requests send no account cookies or authorization, have a 1 MB response limit, DNS/request deadlines, and a three-redirect limit. Login, paywall declarations and unsuccessful HTTP responses produce an upload/paste alternative. No authentication or access restriction bypass is implemented. Imports are limited to twenty recent drafts per workspace per hour and one hundred active drafts.

## Safe draft repair

Open a pending import and choose **Preview reprocess from original** to parse its preserved readable text locally. The preview shows current and proposed contents, the actual count of method rows moved and the valid Pantry matches retained for unchanged source lines. Previewing changes nothing and makes no paid extraction request. Applying requires explicit confirmation that draft edits will be replaced; a snapshot of the current draft is retained with the repair. The operation updates the same draft, checks its revision and leaves original text, file and hash untouched. Approved and cancelled imports cannot be reprocessed, and no recipe is created or modified by repair.

PDF/photo sources without preserved readable text require manual review; the repair action does not start OCR. Unknown quantities, yield, conversions and costing still need review after repair. Valid Pantry matches are retained, while automatic Pantry creation, stock movements and accounting entries are absent from reprocessing.

## Direction-classification regression and verification

The generic parser previously stayed in ingredient mode after a custom heading such as “Crumble topping:”. It parsed the numbered method lines as ingredient quantities and returned no instructions. The review, approval and detail view already shared the `instructions` field; extraction was the failing boundary. The former CookBook-only workaround hid this failure from its adapter tests and discarded the custom method heading. Both paths now use the shared classifier.

The exact supplied “Best Crumble Topping” shared text is retained as `src/test/fixtures/best-crumble.ts`. Regression tests verify six required ingredients, one optional choice, five ordered method steps and the custom heading; separate source URL; unknown yield/times; unresolved ranges; and classification of every nonblank source line. Additional cases cover unnumbered/passive instructions, nonstandard headings, multiple sections, wrapped paragraphs, directions containing measured quantities, ingredient preparation words and absent methods.

The focused suite passed 91 tests in eight files, including mocked structured/OCR extraction, React review/detail rendering, content movement and reordering, preview/confirmation/revision checks and a mocked workspace API sequence of draft save → reopen → approve → recipe edit → refreshed workspace. It verified no Pantry creation, stock or accounting writes in the tested path. TypeScript checking also passed. These checks did not run a browser session, live OCR, a live deployment write or a repair of a user's saved draft.

## Save diagnostics and conversion review follow-up

The fixed five-column table put a complete conversion editor inside a roughly 200-pixel cell. Its 1,000-pixel minimum width also forced horizontal scrolling on smaller screens, and an expanded editor stretched every cell in its row. Ingredient cards now keep quantity, unit, parsed name and Pantry confirmation together. Original text editing, group, preparation, classification, split and remove controls live in native expandable details. The conversion editor opens beneath the card at full width, identifies its Pantry ingredient, and shows both sides of the equation, friendly source labels, notes, verification and adjacent Save/Cancel actions. Collapsing either section preserves its state. The modal body scrolls independently of its footer.

Existing verified conversions are read from the selected Pantry ingredient and passed to the unchanged conversion calculation. A valid saved relationship is reused immediately. Explicit editing prefills a relevant saved measurement; a missing measurement starts with a blank destination amount. Saving updates workspace ingredients through the existing authenticated conversion service and recalculates the review cost without replacing the recipe draft. Ingredient-specific verification remains mandatory. The regression fixture's 125 g per cup is synthetic test input, not a supplied flour conversion.

Both save actions were traced separately. Draft saving was already enabled without complete matching, yield, prices or conversions; incomplete costing did not explain its failure. A reproduced shared failure occurred **after submission and before either import handler**: the workspace endpoint ran unrelated compound costing and tax/account initialization first. Missing settings threw while reading tax rates; a broken unrelated compound could also throw. Import requests now enter their authorized handler before those unrelated calculations and writes. This removes that shared failure path without changing account, billing or recipe approval rules. The owner's exact production exception was not available and has not been attributed to this reproduction.

A second reproduced draft failure occurred after an earlier save had committed but its response was lost: retrying the same draft with its previous revision was rejected as a conflicting edit. Identical saved content now returns the same record without a new write; different stale edits still return a conflict. Lookup by stable import ID is no longer limited to the first 200 queue rows. The workspace lock, business filters, forced row-level policies and atomic recipe/relational-line transaction remain in place.

Before submission, approval requires a title; positive yield and yield unit; at least one ingredient; positive quantities and known units; ingredient names; explicit US/metric cup selection; confirmed valid Pantry matches or explicit new-ingredient decisions; resolved unclassified/method content; and any applicable duplicate/version decision. New package/case ingredients still require physical contents and a storage unit. Missing source instructions require review when the source contains directions. Missing prices and conversions remain costing gaps rather than newly introduced approval blockers. The client and server share the same approval checks, and the footer links each blocker to its affected field or ingredient. Draft saving remains available during incomplete review.

Client schema failures state that no request was sent and identify invalid fields inline. Request/server failures retain the open editor and include an HTTP status and sanitized diagnostic reference/stage when available. Expired access offers sign-in in a new tab so the editor can remain open. Unsaved work receives a browser navigation warning, including when navigation follows session recovery. Repeated clicks are guarded, malformed success responses do not produce a success notice, and a failure to refresh the recipe list after a committed approval is reported separately from save failure. General-purpose import diagnostics contain only stage/category/reference metadata, never recipe contents or credentials.

`src/lib/recipe-import-database.test.ts` uses disposable PGlite PostgreSQL with the actual migration chain and a restricted application role. Identity and database connection discovery are test adapters; SQL execution, constraints, row policies and transactions are real. Six tests cover incomplete draft save/retrieval/edit, a lost-response retry, conflicting edits, one-time approval, normalized recipe lines, missing conversion cost, verified conversion reuse without duplicates, recalculated cost, manual recipe save, invalid fields, an expired session, independence from missing settings/broken unrelated costing, rollback after a genuine numeric SQL failure, and stable-ID lookup beyond the queue limit. These are isolated SQL tests, not writes to Netlify Database or a production login test.

`tests/recipe-import.spec.ts` drives the actual app with a synthetic API at `http://localhost:8889`, using the Vite child server on port 3000 for development modules. It covers the reported **8 cups bread flour** case at widths 1440, 1024, 390 and 720 pixels; 720 pixels tests the reflow equivalent of 200% zoom on a 1440-pixel display, not a real browser zoom setting. Tests cover save failures, preserved edits, draft reopen after refresh, conversion setup/cancel/save, keyboard field order, verified conversion reuse and cost, compact neighboring cards, approval and bounds/overflow. Browser persistence is mocked; database behavior is covered separately by the SQL suite. No live recipe retrieval, OCR or owner recipe was used in this follow-up.
