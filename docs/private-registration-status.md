# Private registration implementation and remaining release gates

> Historical implementation record. Square integration and its setup requirements were retired; see [the retirement record](./square-subscription-billing.md). For current connection evidence, see [Stripe status](./reviews/stripe-connection-status.md).

## Current scope

The first audit and screen/data proposal is in [the registration plan](business-registration-signup-plan.md). The owner approved implementing the existing draft Free scope (5 active recipes, 5 active products, 10 actively tracked inventory items) and the proposed next-renewal/no-proration/7-day renewal-grace policies **for Sandbox development**, while keeping public acceptance, admission, activation and live billing closed. These approvals did not provide legal documents, authorize beta admission or approve tax treatment.

Implemented a private foundation using the existing Netlify Identity provider, Netlify Database, central plan registry and cream/logo-purple design. No production customer backfill/reset, complimentary grant, Square catalog creation, subscription or charge was performed. All applied migrations were preserved; one additive migration adds private registration/billing infrastructure and policies. The earlier Hibbs content-reset migration was not modified or rerun.

## Working private-development surfaces

- `/signup` shows Join the beta, validated plan interest and honest closed-registration status. It collects neither credentials nor legal acceptance and makes no fake beta submission. Pricing preserves stable IDs and never transmits client prices as authority. The managed Identity validation hook denies account creation independently of the UI. Existing login and provider-owned password reset callbacks remain in place; password visibility and safe account routing are supported.
- `/onboarding` authenticates against current Identity, requires verified email and a platform-admin role, and requires an explicitly enabled private test context. Ordinary Owners, user-editable metadata, a query parameter and production context cannot enable test provisioning. No beta user admission workflow is activated. Drafts save to SQL, not browser storage, and resume by verified identity.
- Business setup includes name, region, IANA timezone, explicit USD-only reporting, US/metric preference, optional phone/link/description/focus and a separate initially unchecked test marketing preference. Logo uploads are explicitly not connected to this form. No home address, permit, tax ID or compliance claim is required. Display preferences affect new input defaults; existing normalized quantities and conversions are preserved.
- Private Free provisioning requires a saved profile and a separately read/unchecked development consent fixture. Fixture version, server timestamp and identity are persisted with database-enforced test-only markers; they cannot become production legal acceptance. It creates an empty workspace, Owner membership, independent test billing state, standard units and Cottage Purple settings. Existing membership wins; missing/inactive membership cannot silently seed a new customer workspace. Paid test intent is saved, but paid activation is blocked.
- Workspace entry and API verification checks prevent customer provisioning as a GET side effect and prevent unverified access. Workspace loading no longer displays developer demo records while waiting for private data. Explicit isolated anonymous demos remain separate. New real-form defaults no longer assume sample vendors, prices or recipe ingredient IDs.
- New managed test workspaces enforce SQL-backed Free active-record counts under the existing workspace mutation lock. Cost-only stock is excluded, corrections to counted records stay possible, and paid plans have no small caps in the central rules. Free workflow checks deny paid imports/finance/designer actions; full ingredient/packaging tracking is required before Free completion. Standard-label subset readiness remains a release blocker rather than granting full designer access. Existing production workspaces are not automatically assigned plans or restricted.
- A resumable, skippable checklist is saved in the registration draft. No sample transactions, mandatory team invitations, AI or shopping configuration is introduced.
- `/workspace/billing` checks verified identity and active Owner membership server-side, shows actual assigned/test state or honestly unassigned state, and offers status refresh without a charge. It contains no sample invoices, fake next-billing date or invented portal. No charge, card-update, cancellation or plan-change button claims connectivity that is not implemented.
- `/platform-registration` is independently platform-admin protected and shows stage counts, sanitized event processing state and grant audit metadata. It does not expose business contents, passwords, tokens, card data or raw webhook payloads. Sandbox event checks can be explicitly requested by a verified private tester with rate limits.
- `/verify-email` and `/recover` explain current provider flow and readiness restrictions. Request/resend sends remain disabled until email configuration and authorized recipient testing exist. No accepted-as-delivered email claim is made. `/help` remains public and explicitly says that public contact collection/site/mailbox are not operational; authenticated support remains available to existing accounts. Neither the planned support domain/mailbox nor a personal address is presented as a working public contact.

## Sandbox billing foundation — not a working checkout

The billing state evaluator separates verification/setup, Free, pending/processing, settled paid periods, renewal grace, cancellation, expiry and independently verified complimentary grants. A valid paid period requires correlated workspace/subscription/invoice/payment evidence, completed payment, correct currency/amount, verified period boundaries and no unresolved refund/dispute coverage. Redirects, plan labels and ACTIVE subscription status do not activate paid access. Seven-day grace applies only to prior verified paid coverage. Selecting Free cannot abandon unresolved provider collection. Historical reads/export remain membership/role protected and data is preserved after expiry/downgrade. Deferred features remain denied even for a complimentary plan.

This evaluator is a tested foundation, **not a claim that provider coverage is fully integrated**. Current callable provisioning activates only cardless private Free fixtures. No paid plan is activated. Checkout, stored-card management, self-service subscription cancellation, scheduled plan swaps and automatic verified-period grants are not yet connected. Hosted recurring checkout remains the preferred conditional design from the audit; final choice requires proof of correlation, recurring tax/consent, duplicate prevention and management capabilities. An integrated Square SDK/Cards/Customers/Subscriptions implementation remains the alternative if hosted checkout cannot meet those requirements.

The Square adapter has only a fixed Sandbox origin and refuses operation outside explicitly enabled private development/preview contexts. It requires separate Sandbox account configuration and a pinned API version; there is no Production credential or URL path. No raw card collection is implemented. There are no live plan IDs or charges.

`/api/square/sandbox/webhook` verifies the exact configured URL/raw body HMAC, rejects mismatched merchant/signature/shape, and persists deduplicated references only. It does not persist buyer details or the original webhook body. The worker retrieves canonical Sandbox objects with bounded timeouts and retries, but leaves events in `needs_review` until hosted correlation, invoice/payment settlement and period evidence can be proven. It never activates paid access, modifies a grant or posts platform revenue into bakery accounting. It processes one event per invocation to bound provider time and lock duration. Scheduled functions normally run on production deploys, where this worker is deliberately disabled; private preview testing uses the protected explicit operation instead of assuming preview cron delivery. Duplicate/out-of-order events do not become an entitlement state reducer.

## Private configuration and test boundaries

Private testing is off by default. The implementation requires the platform-provided non-production context, an explicitly enabled `REGISTRATION_PRIVATE_TESTS_ENABLED` control and an existing currently verified `platform_admin` identity. This is not a new beta admission process or a way to create/promote accounts. Initial admin-role setup must use the existing authorized administration process; there is no code bootstrap or email-based promotion.

Sandbox reads/webhooks additionally require `SQUARE_SANDBOX_ENABLED`, isolated Sandbox access, merchant, webhook URL/signature and API-version configuration. Configure these securely in Netlify; never paste their contents into chat, source or browser forms. Merely supplying credentials cannot enable public registration or live payments. The signature endpoint must be reachable by Square despite preview site protection; its signature checks are separate from application login.

No Square seller authorization, actual catalog/region eligibility, recurring tax treatment or real billing account was verified in this implementation run. No Sandbox transaction, real email delivery or real-device browser test was performed. The provider validation hook still needs a deployed direct-endpoint smoke test; checking frontend controls alone is insufficient. Native Identity invite-only settings, recovery/verification provider limits and custom-domain callbacks remain account-side checks.

## Proposed invite-only beta process — owner review required

Keep Join the beta as an informational closed CTA until a real review workflow is approved. The owner designates reviewers, admission criteria, test cohort, approved sender/support contact and retention. A protected reviewer records an admission decision; only then does the existing provider issue an expiring invite to the approved test identity. A provider invite establishes identity only; app workspace invitations carry separate single-use hashed tokens, recipient, workspace/role and seat checks. Verified acceptance of a valid workspace invitation must take precedence over business creation. The current globally unique membership identity prevents multi-workspace membership, so incompatible invites must be rejected rather than silently changing ownership or creating another business. Implementing customer invitations/admission is deferred; none were sent and no reviewer powers were automatically granted.

## Retention proposal — no destructive cleanup enabled

Propose 7-day expiry for unclaimed safe signup intents and removal of safe abandoned drafts after 30 days, excluding any activated workspace, paid account and durable business data. Retain immutable fixture consent/audit separately. Rate-limit counters can expire after their windows, with bounded cleanup within 48 hours. Production consent, billing and accounting retention need reviewed legal/accounting periods. Provider account deletion and Blob cleanup require an explicit reviewed workflow. This run did not activate account deletion, destructive cleanup or production retention jobs.

6. Secure Square Sandbox account setup, recurring checkout/card collection, reliable order-to-subscription correlation, approved tax/consent, exact invoice/payment-period coverage, cancellation, payment-method changes, safe retries/plan swaps, abandoned checkout resolution and the complete Sandbox matrix.

Existing seller subscriptions must be inspected first; no grant is authorized by a name/email, no duplicate workspace is created, and no existing live subscription is modified. Grant storage and evaluator support do not mean the grant exists.
8. Real iPhone Safari/Android Chrome/tablet and desktop keyboard/zoom/keyboard-visibility checks, plus deployed concurrency proof. Component tests and fake transports are not those tests.
9. Explicit approval for public signup and live billing after every release gate passes. Public acceptance, activation and live checkout remain blocked.

## Validation performed

The focused suite passed **127 tests across 11 files**, including existing workspace/plan coverage, component behavior, safe plan routing, empty-workspace rendering, billing evidence rules, webhook signatures/deduplication, manual reconciliation with fake transport and actual SQL policies/constraints in a disposable PGlite database loaded with the complete migration chain. Free recipe/product/stock caps, cost-only exclusions, membership reuse, fixture consent immutability, cross-identity denial, inactive memberships, paid-intent bypass denial, pending checkout uniqueness and preservation of grant records during out-of-order event checks were covered. Fixture HTTP handlers never called real providers.

TypeScript checking and whitespace validation passed. Route metadata was generated with TanStack's route generator without starting a server or running a build. No migration was applied to a deployed database by this run. No actual Square Sandbox, production payment, email delivery, multi-instance concurrency or real-device acceptance result is claimed. Those remain distinct release gates.
