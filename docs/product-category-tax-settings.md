# Product categories and category-based tax settings

The product editor replaced free-text category entry with a workspace category search and native dropdown. Add category and Manage categories operated inside the existing product dialog. Creating a category selected its stable ID for the current draft while retaining other edits. Names were trimmed, whitespace-normalized, and checked for case-insensitive duplicates under the existing workspace transaction lock. Categories required an explicit Food or Non-food classification at creation. Existing unclassified records retained their review status. Inactive or unavailable saved selections remained visible rather than being silently replaced.

Categories, classification mappings, and their revision were persisted in the workspace's existing Netlify Database settings record. Product associations used `productCategoryId` in their existing persisted data. This used the application's existing extensible JSON schema and required no new tables, schema migration, or applied-migration changes. Product categories remained separate from the pantry category model. Renaming retained the ID and prior names for existing name-scoped tax rules, without rewriting products or tax rules. Prior category names were reserved against accidental reuse and ambiguous rule matches.

Tax settings exposed separate Food and Non-food dropdowns using IDs, labels, jurisdictions, and percentages from the existing configured rates. Multiple configured rates could be selected to retain multiple jurisdictions. The existing legacy business default was resolved by the same shared configuration helper; no second tax-rate list, new rates, or jurisdiction assumptions were introduced. Empty treatment selection meant Not configured, not Tax exempt. A configured zero-percent rate remained an explicit configured rate. Missing lists produced retryable errors; they did not masquerade as empty configuration. Product editors linked to tax settings in a new tab to preserve the open product draft.

New products created through the editor used category-based inheritance. The read-only summary showed the selected category, its classification, and the inherited configured treatments or the precise configuration gap. The existing tax engine retained scope checks, jurisdictions, active/effective dates, calculation order, inclusive/exclusive pricing, and compounding. Incomplete configuration could be saved with the product, but future tax calculation required a configured applicable treatment; missing configuration was never treated as exemption. Existing legacy calculations and explicit overrides retained their original behavior. Profitability reporting displayed unavailable pricing when tax configuration prevented a calculation.

Every existing product retained its saved tax source, tax status, rate IDs, and per-rate overrides on edit. Selecting a category did not switch an existing product's taxes. The editor showed both the preserved current assignment and proposed inherited treatment, and flagged differences in applicable rate IDs, percentages, jurisdictions, behavior, order, and compounding as migration conflicts. Category management included the same review of existing assignments. Unavailable saved treatment IDs remained explicit. This comparison covered current effective rules; owner review of future-dated rules and tax obligations remained necessary. Existing import/API callers without the new inheritance fields retained legacy behavior. No automatic bulk migration, classification guess, merge, deletion, or historical reclassification was performed.

Classification changes and mapping changes showed linked-product counts and required explicit confirmation, including zero-product changes. The server independently recomputed the affected count, required the expected settings revision, and serialized changes within the existing tenant transaction. Owner and Manager roles could manage categories and mappings; other roles could not mutate them. The API accepted no client business ID and resolved every list and association within the verified workspace. Generic settings saves could not bypass category-management or confirmation checks. Cross-workspace category links were rejected.

Approved configuration changes affected future category-based calculations. New sales recorded the category/classification context alongside the existing tax snapshot. The existing explicit sale-level rate selection continued to override the inherited selection for that sale only; its snapshot distinguished configured and actually used rate IDs and recorded the override. It did not alter the product's inheritance. Completed sale snapshots were not updated. Classification did not drive pantry field visibility: Packaging kept its existing dedicated rules, stored declarations and units were retained, and other Non-food classifications did not hide ingredient controls. Product-dialog mobile styles also corrected inherited flex rules that squeezed the new category controls and existing packaging inputs.

## Owner-reviewed migration proposal

No migration of business data was executed. For legacy free-text categories, the proposed mapping was one unclassified category per distinct exact saved name, followed by stable-ID association of the products carrying that exact name. Capitalization, whitespace, and renamed-name collisions required an explicit owner decision; they were not merged automatically. The management view listed the current workspace's legacy names and product counts for review. The owner needed to approve the exact name-to-ID mapping and assign classifications; no Food/Non-food guesses were made.

Tax migration remained a separate review. For each existing product, review its current exemption/zero-rating, selected rate IDs, per-rate behavior/order/activation, price-tax mode, and any scope/effective-date rules against the proposed classified treatment. Resolve differences in rate membership or tax behavior explicitly. An approved later migration would switch only the reviewed product IDs to inheritance, retain an audit of the prior assignments, and affect future calculations only. A matching treatment also did not trigger an automatic switch. No bulk “approve migration” operation was included in this change.
