# Existing-account login investigation

The diagnostic `3e4fab8b-991f-4c92-966a-eb6ed4e2b86b` was found in historical production function logs. The logs recorded authentication, a found membership, authorized workspace resolution, and `workspace:ACTIVE_MEMBERSHIP` repeatedly. The live site API and unauthenticated account-access response independently identified `https://mycottagepantry.com`, production deployment `6aef763de601843de47acf09`. A preview/published session mismatch did not explain this incident.

The published login JavaScript was inspected as well as the repository source. After successful `/api/account-access`, it awaited `resumeSelectedPlan()` before navigating. That helper posted `action: resume` to `/api/signup-plan`. A caught failure set an access error and returned before the redirect. Thus the banner actually stopped automatic entry even though the separate business authorization had succeeded. The existing `/oven` recovery link still passed through normal authorization, but appeared beside the plan-reselection link as explanatory text.

The exact displayed message originated from the server's `409 PLAN_SELECTION_EXPIRED` branch. That branch rejected a saved signup reference when its row was missing, belonged to another identity, or was unclaimed and expired. It ran only without an explicit resolved plan or an existing claimed preference. Invalid URL-plan parsing produced a different message; a valid explicit plan took a different server branch. The affected path obtained its saved reference from verified provider metadata or the HttpOnly `cp_signup_intent` cookie, not localStorage or sessionStorage. The original diagnostics did not log that reference source or distinguish the three rejection conditions. The user's browser reference and full provider metadata were unavailable, so those details could not be reconstructed conclusively.

The live Identity lookup confirmed the reported account existed and had a confirmed email. Read-only queries on the available database branch found its identity-linked active Owner membership in the original `Hibbs Homestead` business (`8081ae5d-576f-4bf6-8dd4-a69b39a47bf1`), created October 31, with settings named `Hibbs Homestead Market`, 30 ingredients, 4 recipes, and 5 products. That snapshot had no billing row, no Free-registration marker, no claimed signup intents for this account, and no anonymous signup intents. Existing server rules classified that configuration as legacy complimentary access and imposed no plan restriction. It was not an assigned paid tier. Direct production-database inspection returned HTTP 401, so these database observations represented the available branch snapshot, not a fresh production inventory. No membership, subscription, entitlement, or business record was modified.

The change removed signup-plan resolution from existing-member entry on login, signup, verification, onboarding, and business selection. Only verified accounts without a business continued resolving preferences for setup. Ordinary navigation stopped inheriting ambient plan parameters or redirecting existing users to billing because of a saved selection. An intentional validated return to billing remained supported. Existing-business recovery became a prominent button-styled link before retry controls, with plan-reselection guidance limited to new-business setup. Server Identity verification, membership enforcement, tenant isolation, billing enforcement, and workspace API authorization were retained. No email-based grant, paid-plan prerequisite, duplicate account, duplicate business, or browser-data reset was introduced.

Validation passed 187 focused tests across 12 files, covering account entry, provider verification, membership resolution, signup-reference expiry and isolation, registration, billing, seat policies, and new-business plan continuation. TypeScript and formatting/whitespace checks passed. Focused lint passed for the other changed files and for the account-access client with its pre-existing `react-hooks/set-state-in-effect` rule disabled on the command line. That existing violation was verified against the unchanged baseline; no source suppression was added, and an existing redundant assignment was removed. No build command was run.

Six Chromium browser scenarios passed at desktop and mobile widths. They exercised the edited pages at the intended browser origin with every request intercepted: assets came from local Netlify dev, while authentication and business responses were synthetic. Ordinary login, an unavailable saved-reference cookie, and a retired plan URL each opened the same synthetic business, survived refresh, signed out, and signed back in. The stale cookie remained present. All scenarios made zero plan-resolution requests and zero business writes. These were browser regression tests, not authenticated production acceptance tests.

Live unauthenticated checks returned HTTP 200 for `/login`, `signed_out` from `/api/account-access`, and HTTP 401 from `/api/workspace`. A fresh login to the real Hibbs account and opening its production data after deployment remained unverified because no authenticated user browser session or credentials were available. The production logs proved the original authentication and membership checks had succeeded; they did not prove the patched deployment had opened the business.
